# 5. P0-01 — ROLLBACK FAILURE CAN DISCARD RECOVERY EVIDENCE

**Severity:** P0  
**Type:** Data safety  
**Source:** `scripts/core/workspace_store.gd:352–365`

В `save_document()` при ошибке обновления manifest выполняется rollback к предыдущему override.

Однако результат rollback не проверяется.

Текущий фрагмент логики:

```gdscript
if not recorded:
    var had_previous := FileAccess.file_exists(backup)
    if had_previous:
        transactional_write_abs(
            target,
            FileAccess.get_file_as_bytes(backup),
            "",
            {},
            false
        )
    elif FileAccess.file_exists(target):
        DirAccess.remove_absolute(
            ProjectSettings.globalize_path(target)
        )

    commit_transaction(str(res.get("journal", "")))
    return {
        "ok": false,
        "error": "manifest update failed; previous override restored"
    }
```

Проблема:

- Rollback может завершиться ошибкой.
- Результат восстановления игнорируется.
- Исходный transaction journal удаляется.
- Пользователь получает сообщение, утверждающее, что предыдущая версия восстановлена.

Это противоречит safety contract.

### Required implementation

Ввести проверяемый rollback transaction outcome.

При ошибке manifest update:

1. Попытаться восстановить предыдущую версию.
2. Проверить результат операции.
3. Проверить фактические bytes/hash восстановленного target.
4. Если rollback успешен, завершить исходную транзакцию.
5. Если rollback неуспешен, сохранить исходный journal и recovery metadata.
6. Вернуть `RECOVERY_PENDING` либо `UNRECOVERABLE` согласно реальному состоянию.
7. Не выдавать сообщение «previous override restored», если восстановление не доказано.

Продумать ситуацию, когда rollback сам создаёт новый journal для того же target. Исключить преждевременное удаление исходных recovery данных.

### Test matrix

```text
Initial override: 200
New working value: 250

Inject manifest write failure
Inject rollback write failure

Expected:
- saved 200 remains recoverable
  OR
- valid 250 with explicit pending reconciliation

Never:
- silently lost previous revision
- deleted last usable journal
- false "restored" message
```

Дополнительно проверить:

- Rollback failure после удаления target.
- Rollback failure после временной записи.
- Manifest failure при первом сохранении.
- Manifest failure при повторном сохранении.
- Recovery после полного нового запуска процесса.

**Acceptance:** ни одна ошибка rollback не приводит к удалению единственной записи, позволяющей восстановить данные.

# 6. P0-02 — RECOVERY JOURNALS ARE NOT SUFFICIENTLY PATH-VALIDATED

**Severity:** P0 safety boundary  
**Source:** `scripts/core/workspace_store.gd:211–302`

`recover_transactions()` читает JSON journals из workspace.

`_recover_one()` использует содержащиеся там:

```text
target
temp
backup
source
rel
md5
size
```

В текущем коде нет достаточной проверки, что операции над `target`, `temp` и `backup` остаются в разрешённых областях.

Программа доверяет значениям из journal.

При повреждении, случайном изменении или подмене записи recovery потенциально может:

- Удалить неподходящий target.
- Записать восстановленные bytes по нежелательному пути.
- Перенести временный файл за границы workspace.
- Привязать произвольный source/rel к manifest.
- Нарушить read-only policy проекта.

В архиве не обнаружено evidence такого инцидента. Это статически установленный недостаток проверки входных данных.

### Required fix

Создать строгий transaction-path validation layer.

Каждый journal должен быть связан с operation type и разрешённым root.

Проверять:

1. Canonical target path.
2. Allowed root.
3. Operation type.
4. Expected temporary sibling.
5. Backup location.
6. Journal filename/target identity.
7. Target hash and byte count.
8. Valid relative ODF path.
9. Manifest source mapping.
10. Consistency of operation metadata.

Для Workspace ODF transactions разрешать только ожидаемые paths внутри workspace.

Для export transactions использовать отдельно зарегистрированный staging root.

Не проводить recovery по произвольному абсолютному пути из JSON без дополнительной проверки.

Если journal не проходит проверку:

```text
status: UNRECOVERABLE
reason: INVALID_TRANSACTION_PATH
```

Сохранить его для диагностики и ничего не изменять по указанным в нём подозрительным путям.

### Tests

Синтетические journals с:

```text

game/Data/file.odf
workshop/content/file.odf
wrong temp sibling
wrong backup path
mismatched target hash
invalid source mapping
```

Все должны быть безопасно отклонены.

Тесты выполнять только на специально созданных временных fixtures.

Не проверять опасное поведение путём записи в настоящую игру.
